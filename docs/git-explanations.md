# Git: пояснения для защиты практической работы

Это учебная памятка. Примеры команд поясняют смысл операций; выполненные действия и реальные хеши нужно смотреть в журнале конкретного репозитория.

## Дополнительные вопросы

**Кто и зачем написал Git?** Линус Торвальдс создал Git в 2005 году для разработки ядра Linux: сообщество потеряло возможность продолжать прежнюю работу с BitKeeper из-за лицензионного конфликта. Нужна была подходящая для распределённой разработки замена. Первый коммит самого Git датирован 7 апреля 2005 года. [Интервью Торвальдса, GitHub, 2025](https://github.blog/open-source/git/git-turns-20-a-qa-with-linus-torvalds/).

**За какое время появилась первая версия?** Корректный ответ — примерно за 10 дней появилась версия, которой Торвальдс уже мог пользоваться для работы над ядром. В том же интервью он уточняет, что обдумывал устройство системы около четырёх месяцев. Поэтому «Git целиком написан за 10 дней» — слишком широкое утверждение: это срок начальной реализации, а последующее развитие продолжается годами. [Интервью Торвальдса, GitHub, 2025](https://github.blog/open-source/git/git-turns-20-a-qa-with-linus-torvalds/).

**Чем Git отличается от других систем контроля версий?** Git распределённый: обычный полный clone даёт локальный репозиторий с историей; коммиты и просмотр этой истории доступны без сервера. Ветки позволяют вести несколько линий разработки. Это отличает Git от централизованных систем, но распределённость есть и у других систем. [Git User Manual](https://git-scm.com/docs/user-manual).

**Как Git хранит изменения?** Логически коммит описывает снимок проекта. Объекты `blob` хранят содержимое файлов; `tree` — имена, режимы и ссылки на файлы/подкаталоги; `commit` — ссылку на корневое дерево, родителей, автора и сообщение. Объекты адресуются хешем. Одинаковое содержимое можно использовать повторно; каждый коммит не создаёт независимую полную копию всех файлов. Разницу версий Git вычисляет при сравнении. [Pro Git: Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects.html).

**Что такое GitHub, GitLab и Bitbucket?** Это платформы размещения репозиториев и совместной работы с кодом, его историей и обсуждениями. Git — сама система контроля версий; удалённая платформа предоставляет место для публикации репозитория и совместной работы. [GitHub Docs: платформы размещения кода](https://docs.github.com/en/migrations/overview/migration-paths-to-github).

## Основные команды

| Команда | Что происходит |
| --- | --- |
| `git add fibonacci.py` | Текущее содержимое файла попадает в индекс — подготовленный снимок следующего коммита. |
| `git commit -m "Add Fibonacci implementation"` | Создаётся коммит из индекса. Последующие правки файла в этот коммит автоматически не попадут. |
| `git checkout -b feature` | Создаётся ветка `feature`, и рабочая копия переключается на неё. |
| `git merge feature` | Изменения `feature` объединяются с текущей веткой. При расхождении истории обычно возникает коммит слияния; при fast-forward достаточно передвинуть указатель ветки. |
| `git cherry-pick HASH` | Изменение выбранного коммита применяется к текущей ветке и обычно записывается новым коммитом. |

Источник таблицы: [Git User Manual](https://git-scm.com/docs/user-manual).

**Конфликт** означает, что Git не смог автоматически объединить изменения. Нужно посмотреть `git status`, исправить файл до желаемого состояния, удалить маркеры конфликта и выполнить `git add FILE`. При слиянии затем выполняется `git commit`; нужно проверить работоспособность полученного кода. [Git User Manual](https://git-scm.com/docs/user-manual).

## Rebase и squash

`git rebase master`, запущенный в рабочей ветке, повторно применяет её коммиты поверх `master`. При изменении родителя получается новый объект коммита с новым хешем. Смысл операции — перенести свою последовательность изменений на новую базу. Уже используемую другими людьми историю переписывают только по согласованию. [Документация git rebase](https://git-scm.com/docs/git-rebase).

`git rebase -i HEAD~3` открывает список трёх последних обычных коммитов, от старого к новому. Чтобы объединить их, первый оставляют `pick`, а у следующих выбирают `squash`:

```text
pick   a1b2c3d Add initial function
squash b2c3d4e Improve function
squash c3d4e5f Add example
```

Хеши здесь условные. `squash` объединяет изменения и позволяет отредактировать итоговое сообщение; `fixup` отбрасывает сообщение присоединяемого коммита. После конфликта во время rebase: исправление файла, `git add FILE`, `git rebase --continue`. Отмена всей операции: `git rebase --abort`. [Документация git rebase](https://git-scm.com/docs/git-rebase).

## Восстановление через reflog

`git reflog` показывает локальную историю изменения ссылок; журнал `HEAD` включает переключения веток. Если коммит пропал из текущей линии истории, найдите его хеш, посмотрите содержимое и создайте на нём ветку:

```bash
git reflog --date=iso
git show HASH
git branch recovered HASH
git checkout recovered
```

`HASH` заменяется найденным хешем. Reflog помогает найти объект, а созданная ветка снова делает его доступным по имени. Записи reflog могут истекать; это не бессрочная резервная копия. [Документация git reflog](https://git-scm.com/docs/git-reflog).

Для сдачи сохраняют журнал отдельным файлом и добавляют его в репозиторий:

```bash
git reflog --date=iso > git-reflog.txt
git add git-reflog.txt
git commit -m "Add Git practice reflog"
```

Файл отражает состояние журнала на момент сохранения. Коммит, который добавляет этот файл, закономерно ещё не указан внутри него.
