# Локальная практика Git

Автор: Леонов Никита Олегович. Группа: 15-25.

Это отдельный учебный репозиторий `git-local-practice`. Сценарий — сопровождение
небольшой программы Фибоначчи и её документации. Команды выполнены реально;
`git-practice-transcript.txt` содержит команды, вывод Git и изменения файлов.
Хеши ниже относятся именно к этому учебному репозиторию, а не к fork преподавателя.

## Запуск

Нужен Python 3, сторонние библиотеки не требуются.

```sh
python fibonacci.py 20
```

Результат: `6765`. На Windows с установленным Python также работает
`py -3 fibonacci.py 20`. Файл `settings.txt` хранит согласованный пример для
документации; программа получает число явно из аргумента командной строки.

## 1. Add, commit и switch

`git init --initial-branch=main` создал отдельный репозиторий. Настройки автора
заданы через `git config user.name` и `git config user.email` только в нём.

`git add fibonacci.py settings.txt README.md` поместил текущее содержимое этих
файлов в индекс. `git commit -m "feat: add iterative Fibonacci example"`
сохранил снимок индекса: `acd48521908c45b758937968c40939879ea4005c`.

`git switch -c docs/launch` создал ветку от текущего коммита и переключил на неё.
В ней добавлена инструкция запуска, коммит `2050fdd9ab71971e31a7d49bcd25dbd58730603a`.
`git switch main` вернул рабочую ветку к `main`.

## 2. Merge

В `main` отдельно добавлен журнал изменений — `af89bfe9e2239fbed3b153ffdd4d4102ce287849`.
Ветки разошлись. Команда

```sh
git merge --no-ff docs/launch -m "merge: include launch instructions"
```

создала коммит слияния `c0c60b712a193c8a710c59d43ff16f5fda70babe` с двумя родителями.
Обе независимые истории сохранены. `--no-ff` явно требует коммит слияния.

## 3. Настоящий конфликт и его разрешение

Ветка `feature/larger-example` изменила единственную строку `settings.txt`
с `example_n=10` на `example_n=20` — `d1ea78b187f877a3f87c6a7beb093dd697161c0b`.
В `main` та же строка независимо стала `example_n=12` —
`3f9c6093b9322407bcbd5854f0df3bb97e0a2490`.

`git merge feature/larger-example` завершился кодом 1 и показал конфликт.
`git status --short` показал `UU settings.txt`. В файле появились маркеры:

```text
<<<<<<< HEAD
example_n=12
=======
example_n=20
>>>>>>> feature/larger-example
```

Я разрешил конфликт редактированием файла: оставил `example_n=20`, добавил
поясняющий комментарий и удалил маркеры. Затем `git add settings.txt`
отметил конфликт как разрешённый, а `git commit` завершил слияние:
`3abf838dd9232d2f4804e6dc5dcfc7f591ca907f`. У этого коммита два родителя.

## 4. Rebase

Ветка `docs/algorithm` получила коммит с объяснением алгоритма:
`8a5e265d83e97dc227378f55a44457fde77ff396`. После этого `main` продвинулась до
`f285025432d9729631c23eb09ee801c30245286e`. На ветке `docs/algorithm`
выполнена команда `git rebase main`.

Git повторно применил изменение документации поверх новой вершины `main`.
Получился новый коммит `2ec9c1aa4aefcb1886c680a7570718d8267d4fb6`: содержимое изменения
сохранилось, но изменились родитель и хеш. Затем
`git switch main` и `git merge --ff-only docs/algorithm` передвинули `main`
вперёд без дополнительного коммита слияния.

## 5. Интерактивный rebase и squash

На ветке `docs/boundaries` созданы три последовательных коммита:

1. `da98f99488433c5412f71a2c00fa9dfa4ae2b23e` — пример для 0.
2. `d7198e045fa00bbb142358a0687e76ef0d2b4381` — пример для 1.
3. `877e7ea0bd412cb86e585a566472ff24d058493e` — пример отрицательного аргумента.

Выполнено именно `git rebase -i HEAD~3`. Для воспроизводимости редактор
списка операций был задан через `GIT_SEQUENCE_EDITOR`: вспомогательный
редактор оставил `pick` у первого коммита и заменил его на `squash` у второго
и третьего. `GIT_EDITOR` задал общее сообщение коммита.
Это обычный интерактивный механизм Git с программным редактированием todo:

```text
pick da98f9948843 docs: add zero input example
squash d7198e045fa0 docs: add one input example
squash 877e7ea0bd41 docs: add negative input example
```

Результат — один коммит `923d766b16f7bbf41c18e17ea94f94d3df5ae36d` с общим сообщением
`docs: combine Fibonacci boundary examples`. Проверка
`git rev-list --count 2ec9c1aa4aef..923d766b16f7` дала `1`.
Все три примера сохранились. Изменённая история ещё не публиковалась.

## 6. Cherry-pick

В `experiment/notes` сначала создан экспериментальный файл
(`a6915601b90885648ce3bd2b5590a03feedb336e`), затем отдельный полезный коммит со справочными
значениями: `6291fa810a7053b7c4d91e461c6e265643930c0c`.

В `main` выполнено:

```sh
git cherry-pick 6291fa810a7053b7c4d91e461c6e265643930c0c
```

Новый коммит: `4b425b9c780fd6204b690dbfaf51444a46479137`. В `main` появился
`KNOWN_VALUES.md`, а `EXPERIMENT.md` не появился: перенесено изменение
только выбранного коммита. Его родитель отличается, поэтому хеш тоже новый.

## 7. Потеря коммита и восстановление через reflog

На специально созданной ветке `practice/recovery` добавлена заметка
`RECOVERED.md`: `c928eb134cecd4a0e1d243152cd49966a2e184c0`. После `git reset --hard HEAD~1`
ветка вернулась к родителю, а заметка исчезла из рабочей папки.
Сброс выполнен только в отдельной учебной ветке с чистой рабочей папкой.

`git reflog --date=iso -8` показал недавние перемещения `HEAD`.
`git rev-parse "HEAD@{1}"` вернул хеш потерянного коммита.
Команда `git branch recovered/notes "HEAD@{1}"` создала на нём ссылку ветки,
а `git switch recovered/notes` восстановила заметку в рабочей папке.
Хеш восстановленного коммита точно совпал с исходным:
`c928eb134cecd4a0e1d243152cd49966a2e184c0`. Затем эта ветка добавлена в `main` через
`git merge --ff-only recovered/notes`.

`reflog` — локальный журнал перемещений ссылок. Он не публикуется обычным
`push`; его записи и недостижимые объекты могут со временем удаляться.
Поэтому восстановленный коммит закреплён веткой, а журнал сохранён файлом.

## 8. Сохранение подтверждений

После описанных операций выполнена команда:

```sh
git reflog --date=iso > git-reflog.txt
```

Файлы `git-reflog.txt`, `GUIDE.md` и `git-practice-transcript.txt` добавлены
в отдельный итоговый коммит. Снимок reflog сделан перед этим коммитом;
поэтому сам коммит с сохранённым журналом в снимок не входит.

## Проверки

- Зафиксирован настоящий конфликт (`CONFLICT`, `UU` и маркеры в файле),
  затем создан успешный коммит слияния с двумя родителями.
- После обычного rebase исходный и новый хеши различаются.
- После `rebase -i` три коммита превратились в один, примеры сохранились.
- Cherry-pick добавил только нужный файл из экспериментальной ветки.
- После reset заметка исчезла; после восстановления через `HEAD@{1}`
  вернулась с исходным хешем коммита.
- Программа проверена на 0, 1, 2, 10 и 20: результаты 0, 1, 1, 55 и 6765.
- Аргумент -1 вызывает понятную ошибку и код возврата 2.

## Что нужно уметь объяснить

`add` готовит содержимое следующего коммита в индексе; `commit` сохраняет
снимок; `switch` выбирает или создаёт ветку. `merge` объединяет ветки,
сохраняя историю. `rebase` переносит изменения коммитов на другую базу
и меняет хеши. `rebase -i` позволяет выбрать действия над коммитами,
в том числе `squash` — объединение нескольких в один. `cherry-pick`
переносит отдельное изменение. Конфликт требует выбора итогового
содержимого и `add` перед завершением операции. `reflog` помогает найти
коммит после перемещения ссылки и закрепить его новой веткой.
